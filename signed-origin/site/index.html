Each time a PDF here is downloaded, the server signs it together with a fresh block hash from Rede Blockchain Brasil. The downloader then records a fingerprint of that signed response on the RBB. Two blocks fix when it happened.

Convinces your browser, right now, that it's talking to the domain. It can't be shown to anyone later, because HTTPS doesn't sign what it delivers.

what we add

the publication signature

The domain signs this exact file at this URL, after a given block. Anyone can save it and check it years later without contacting the server.

the flow

Set up once, then the same five steps for every observation. Recording through a permissioned service with an API key instead? See the relayer variant.

what the server signs

The signature uses the HTTP Message Signatures standard (RFC 9421). It goes on the server's response; the request only carries the nonce. The signed text is four lines:

"@authority";req: apolinar.io
domainwhich site served it
"@path";req: /publicacoes/diario-teste.pdf
addresswhich URL on that site
"content-digest": sha-256=:VuSgsA9HJKmu4adIXgxJv5IKFYxxUooMhiBqR0IqZEQ=:
pdf hashchange one byte and it no longer matches
"@signature-params": ("@authority";req "@path";req "content-digest");created=…;nonce="0x…";keyid="apolinar-2026-1";alg="ed25519"
nonce + keythe nonce is block N's hash, so the signature can't predate N. created is the server's clock and is ignored.
try it live

ask the server for a signed copy right now

Your browser sends a random nonce, receives the PDF with its signature, and checks it against the key at /.well-known/publication-key.json. Real observations use an RBB block hash as the nonce. An HTTPS page can't reach the RBB's plain-HTTP RPC, so this demo uses a random one.

    what goes on the rbb

    Only fingerprints and identifiers go on-chain, a few hundred bytes per observation. The PDF and the signed response stay here, in evidencias/.

    fieldwhat it is
    sourceURLthe observed URL
    documentHashSHA-256 of the PDF
    evidenceHashSHA-256 of bundle.json: request, signature headers, key and block N
    nonceBlockNumber, nonceBlockHashblock N. The contract checks blockhash(N) when recording, so the nonce must be at most 256 blocks (~17 min) old
    keyFingerprintwhich apolinar.io key signed; registered once, before any observation
    registeredAtblock M's timestamp, set by the chain

      For the full check, including the RBB, run the verifier from registro-TLS-rbb. It reads the evidence from this site and confirms block N, the transaction, the event and the key registration on the RBB testnet:

      node scripts/signed-verify.mjs https://apolinar.io/publicacoes/evidencias/<hash>/
      1. the key belongs to the domainits fingerprint was registered on the RBB before the observation, and it's still published at /.well-known/
      2. the signature is genuinerebuild the four lines, verify them with Ed25519
      3. made after block Nthe signed nonce equals block N's hash on the RBB
      4. recorded no later than block Mthe transaction's event carries this exact evidence hash
      5. same documentSHA-256 of the PDF equals the signed hash; the PDF's own signature shows the author

      what the server can't fake

      attemptresult
      set its clock wrongno effect: time comes from blocks N and M
      sign in advanceimpossible: it would need block N's hash before the block existed
      change a file or signature laterimpossible: the evidence hash is on the RBB
      forge past proofs after a key leakimpossible: nothing can be recorded in a block that's already in the past
      serve different files to different peopleexposed: two signed responses with different hashes for one URL are public proof
      serve the file only to the observermitigated by several independent observers the server can't single out

      Each observation is a sample: it proves the URL was online at that moment, not continuously between samples.
